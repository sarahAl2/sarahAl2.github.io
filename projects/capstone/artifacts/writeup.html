2 Abstract

The Northwest Hub needs board-ready reporting without recurring spreadsheet reconciliation across Lightspeed, QuickBooks, and program/grant workflows. Spokes implements a reproducible reporting pipeline using scheduled Python ETL in GitHub Actions, a Neon Postgres warehouse, and Grafana dashboards hosted on Fly.io (The Northwest Hub and Contributors 2026; Neon 2026; Grafana Labs 2026).

The Lightspeed reporting slice is operational and reproducible, while QBO unattended OAuth hardening and program-impact metric development remain partial. The primary research question is answered for the Lightspeed scope: leadership can use live dashboards instead of manual POS spreadsheet reconciliation.

The secondary research question is answered with descriptive trend analysis: directional-change comparisons show sales and ticket count rising faster than average basket size, indicating volume-led growth. All conclusions are bounded to validated data windows and known source limitations.

3 Introduction: Problem and Research Questions

The Northwest Hub tracks operations and finance across multiple systems, including Lightspeed R-Series POS and QuickBooks Online. Before this project, recurring leadership reporting depended on manual exports and spreadsheet reconciliation. This introduced delay, inconsistencies in metric definitions, as well as extra cost to hire a third party bookkeeper to assemble monthly board packets.

The capstone objective is both technical and operational: design a low-cost, maintainable reporting workflow that produces board-usable metrics on a predictable cadence with explicit quality boundaries.

Primary research question

How can The Northwest Hub maintain a reproducible, low-maintenance reporting workflow that consolidates key operations and financial indicators for board decision support?

Secondary research questions

  1. What does trailing-window KPI behavior (sales, tickets, average basket) show relative to prior-window and same-period-last-year baselines?
  2. Are observed changes primarily volume-driven, basket-driven, or mixed, and can this be evaluated using directional-change analysis?
  3. What quality boundaries must be attached to those findings?

4 Impact and Stakeholders

Spokes is designed for stakeholders who currently spend time assembling monthly reporting packets from multiple systems.

Named stakeholder groups

  • Executive leadership.
  • Board members and advisors.
  • Staff who manage their source systems and reports.

Intended impact pathways

  1. Reduce manual reconciliation burden for recurring Lightspeed KPI reporting.
  2. Standardize metric definitions in SQL/query logic rather than ad-hoc spreadsheet formulas.
  3. Keep track and improve decision timeliness by making trend and freshness signals visible in one dashboard surface.
  4. Provide reproducible pipeline and dashboard artifacts so another analyst can maintain or extend the workflow without tribal knowledge.

5 Architecture and Source Integration

  1. Pipeline architecture: GitHub Actions + Neon + Grafana on fly.io replaced a heavier orchestration path to reduce operational overhead while preserving reproducibility (The Northwest Hub and Contributors 2026; Neon 2026; Grafana Labs 2026).
  2. Source integration constraints: both QBO and Lightspeed rely on OAuth-based API access, with different operational failure modes and token lifecycle behavior (Intuit Developer 2026; Lightspeed Developers 2026; Denniss, Bradley, and Sakimura 2017).

This places the project in applied analytics engineering: reproducible descriptive reporting first, analytics engineering second, then expanded source completeness.

6 Data and Data Engineering

6.1 Sources and implemented schema

The warehouse in this milestone is a reporting mart centered on financial_balances, with supporting tables vendor_liabilities and program_impact. The schema is defined in src/fin_balance.py.

  • financial_balances unique grain: (as_of_date, source_system, line_item)
  • vendor_liabilities: payable snapshots by vendor/aging category
  • program_impact: mixed-type program metrics currently stored as text

The reporting view layer is built in src/transform_data.py as three SQL views:

  • view_grafana_monthly_pnl
  • view_grafana_weekly_ops
  • view_grafana_vendor_trends

6.2 Working schema is Lightspeed only.

For the defended Lightspeed scope, the warehouse uses one non-normalized KPI table shape and normalized reporting projections.

6.2.1 Non-normalized table shape (storage)

financial_balances rows where source_system = 'Lightspeed'.

Object Grain Core columns Notes
financial_balances (Lightspeed slice) as_of_date + source_system + line_item as_of_date, source_system, section, subsection, line_item, amount, updated_at KPI values are stored in long format by line_item (POS Sales, Ticket Count, Avg Basket Size), which is intentionally non-normalized for ingestion simplicity and UPSERT stability.

6.2.2 Normalized table/view shape (analysis-ready)

Normalized reporting structure is produced from the Lightspeed slice of financial_balances via SQL views in src/transform_data.py.

Object Grain Core columns Lightspeed use
view_grafana_weekly_ops reporting_week + section + subsection + line_item reporting_week, section, subsection, line_item, total_amount Weekly normalized aggregation for KPI trend panels.
view_grafana_monthly_pnl reporting_month + section + subsection + line_item reporting_month, section, subsection, line_item, total_amount Monthly normalized aggregation for board-facing summaries.

In this milestone, there is no separate physical Lightspeed-only normalized fact table; normalization is applied in the reporting view layer.

6.4 Engineering controls used

Controls implemented for the defended Lightspeed pipeline include:

  1. OAuth token lifecycle control: access-token refresh is handled in code and refresh-token rotation is persisted so scheduled runs remain unattended.
  2. Single-writer refresh protection: advisory-lock gating prevents concurrent refresh writes from revoking shared token chains.
  3. Credential compartmentalization: secrets are loaded from environment variables/warehouse token storage, not committed to source control.
  4. Scope minimization: API scope set is explicitly constrained in code to required Lightspeed read/reporting capabilities.
  5. Cloudflare compatibility hardening: browser user-agent headers are applied to prevent known non-browser request blocking.
  6. Network resilience: retry/backoff logic is applied for transient API and connectivity failures.
  7. Load idempotency: UPSERT semantics on (as_of_date, source_system, line_item) prevent duplicate growth on retried or repeated loads.
  8. Schema-level uniqueness guard: unique-constraint migration/guard is applied to align table constraints with UPSERT conflict keys.
  9. Safe database URL handling: connection strings are sanitized for quote/whitespace edge cases before connecting.
  10. Dry-run by default: pull scripts default to fetch/print behavior; warehouse writes require explicit --load.
  11. Historical backfill control: bounded monthly backfill logic with existing-snapshot checks reduces unnecessary rewrites and API load.
  12. Missing-day repair routine: dedicated daily snapshot recovery reconstructs cumulative KPI rows for coverage gaps.
  13. Post-load dedup validation: dedicated duplicate-detection/fix workflow verifies uniqueness and repairs drift when needed.
  14. Coverage completeness checks: monthly expected-line-item checks flag sparse periods before interpretation.
  15. Freshness observability control: dashboard staleness is computed from updated_at to represent true load recency.
  16. Claim-boundary control: Lightspeed-only production claims are separated from partial QBO/program paths in evidence and conclusions.

Freshness signals in the Data Health Checks dashboard are computed from warehouse write timestamps (updated_at) rather than date-only snapshot keys (as_of_date), so the lag indicator represents true hourly load recency.

7 Ethics and Responsible Use

This project handles private financial and operational information for a community-serving organization. The main ethical focus is data stewardship and claim discipline.

Data handling and confidentiality are governed by a signed NDA with The Northwest Hub; that agreement is managed outside this repository and is therefore not included as a repo artifact. Within the repository, governance controls are evidenced through claim-boundary discipline, source-status labeling, and reproducible pipeline documentation.

Considerations regarding data use and interpretation are framed as responsible reporting and decision support. Potential community harm from misinterpretation is mitigated by explicit claim boundaries, transparent source limitations, and visible freshness/coverage checks in dashboards.

Controls applied

  1. Public-facing artifacts do not expose raw sensitive records.
  2. Credentials are handled through environment variables and secret stores, not committed in source.
  3. Findings are bounded to validated windows and explicitly label partial source coverage. 4.spokes legal and ethical compliance is guided by the NDA with The Northwest Hub, which governs data access and use.

Interpretation boundaries

  1. Results are descriptive, not causal.
  2. Trend changes are decision signals, not proof of intervention impact.
  3. Historical gaps and source incompleteness are reported as limitations, not silently ignored.
  4. Findings are intended for internal decision support, not public dissemination without context.

8 Methods and Evaluation

Methodology combines engineering reproducibility checks with descriptive trend analysis.

8.1 Design

  1. Build a reproducible source-to-dashboard pipeline for recurring board reporting.
  2. Quantify KPI direction and magnitude using trailing-window comparisons.
  3. Attach confidence boundaries through freshness and coverage checks.
  4. Document the pipeline and dashboard so another analyst can reproduce outputs without tribal knowledge.
  5. Evaluate the defended Lightspeed slice of the pipeline for operational readiness and analytical defensibility.

8.2 Analytical procedure

  1. Execute Lightspeed ingestion in dry-run mode to validate token health, API response shape, and mapped KPI rows before any write operation.
  2. Re-run ingestion with --load after validation to UPSERT the daily snapshot KPI rows (POS Sales, Ticket Count, Avg Basket Size) into financial_balances.
  3. Verify snapshot integrity by checking the expected three-line-item presence per Lightspeed as_of_date and resolving sparse/duplicate dates before analysis.
  4. Build reporting projections in SQL views (view_grafana_weekly_ops, view_grafana_monthly_pnl) to normalize KPI totals by reporting period.
  5. Construct trailing 90-day analysis windows for each KPI from the warehouse snapshot and compute comparison baselines.
  6. Define two comparison references for each KPI:
  • prior 90-day window
  • same period last year (SPLY)
  1. Compute directional-change percentages against each reference window and compare relative movement across sales, ticket count, and average basket.
  2. Cross-check interpretation with freshness/coverage indicators (updated_at recency and expected line-item completeness) before finalizing claims.
  3. Classify growth pattern as volume-led, basket-led, or mixed based on whether ticket and sales movement outpace basket movement in the same evaluated window.
  4. Apply claim-boundary rules: report only validated Lightspeed-supported findings and explicitly label non-Lightspeed paths as partial/pending.

Directional change is calculated as:

\[ \mathrm{PctChange}(\%) = 100 \times \left(\frac{C}{B} - 1\right) \]

Where:

  • \(C\) = current-window value
  • \(B\) = baseline value (prior 90-day window or SPLY)

8.3 Evaluation criteria

Engineering readiness

  1. Core scripts run successfully for schema, pull, and transform layers.
  2. Dashboard panels render from warehouse-backed queries.
  3. Rebuild instructions are sufficient for another analyst to reproduce outputs.

Analytical evidence quality

  1. Claims trace to explicit query logic and warehouse records.
  2. Every comparative claim states its reference window.
  3. Limitations are attached when source coverage is partial.
  4. Analysis would benifit from all 3 data sources, but defended claims are bounded to the Lightspeed slice.
  5. Directional-change interpretation is consistent across KPIs and comparison windows.

8.4 Scope boundary

No predictive model training is used. Train/validation/holdout paradigms are not applicable to this milestone. Initial intention was to include QBO and program-impact metrics, and project impacts STEP from google sheets, and produce a predictive model for future sales, but the defended milestone scope is limited to Lightspeed KPI reporting and descriptive trend analysis due to data access delays and time constrains.

8.5 Engineering result: Lightspeed reconciliation workflow replaced

For the Lightspeed scope, the project meets its core operational goal. Leadership can review recurring KPIs from the live dashboard instead of manually reconciling POS exports.

Evidence includes:

  1. Scheduled sync behavior with reproducible load/transform scripts.
  2. Dashboard panels for MTD sales, ticket count, average basket, and confidence checks.
  3. Warehouse and dashboard artifacts versioned in repository paths.

8.6 Analytical result: growth is primarily volume-led

Trailing-window directional-change results defended at poster session:

Metric vs Prior 90D vs SPLY
Sales +46.9% +5.4%
Ticket Count +37.2% +7.8%

Interpretation: sales and ticket growth outpace basket growth, indicating traffic/transaction volume is the dominant driver in the evaluated period.

9 Discussion, Limitations, and Future Work

9.1 Discussion

The strongest contribution is not only trend insight but process reliability: metrics now flow through a repeatable, inspectable path with explicit confidence signals. That is a practical governance gain for board reporting.

An important implication is that automation changes the decision conversation, not just the data refresh speed. Before this pipeline, stakeholders often spent their energy debating spreadsheet versions and reconciliation steps. With a reproducible workflow, that energy can shift toward higher-value questions: which changes are meaningful, which are temporary noise, and what operational action is justified.

This also introduces a productive tension: as dashboards become easier to trust, teams may be tempted to over-trust point estimates. The capstone intentionally counterbalances that risk with freshness checks, coverage signals, and explicit claim boundaries. In practice, the most useful output is not a single KPI value, but a decision context that includes recency, completeness, and uncertainty.

For a community-serving organization, this distinction matters. Reporting systems do not merely summarize performance; they influence decisions that can affect service access, staffing priorities, and resource allocation. A robust analytics workflow is therefore both a technical artifact and a governance artifact: it should make decisions faster, while making assumptions and limits more visible.

9.2 Limitations

  1. Source maturity is uneven: Lightspeed is operational; QBO unattended flow remains incomplete.
  2. Program-impact table values are text-typed, limiting numeric analytics without additional typing/validation.
  3. This work supports descriptive decision intelligence, not causal attribution.
  4. Communication with the hub resulted in less outcome due to time constraints and source access delays, so the defended scope is limited to Lightspeed KPI reporting and descriptive trend analysis.

9.3 Future work

  1. Complete QBO unattended OAuth hardening and remove manual token dependency.
  2. Harden program-impact schema typing and validation rules for numeric indicators.
  3. Expand dashboard confidence checks to source-specific quality flags and alerting.
  4. Introduce optional dimensional decomposition if broader cross-domain analytics requires it.
  5. keep the runbook and dashboard documentation synchronized with the source-of-truth map so handoff instructions stay aligned with live behavior.

10 Conclusions and Recommendations

Spokes achieved a production-relevant milestone for the Lightspeed reporting slice: recurring board KPI review can be performed from reproducible warehouse-backed dashboards rather than manual spreadsheet reconciliation.

The current analytical finding is actionable: growth is volume-led more than basket-led in the evaluated windows. Near-term operations should prioritize traffic and repeat-visit levers while testing basket-lift tactics in controlled cycles.

Recommendations:

  1. Preserve claim boundaries: treat Lightspeed findings as production-grade; treat QBO/program claims as partial until hardening is complete.

  2. Keep freshness and coverage panels visible in executive views to anchor decision confidence.

  3. Sequence phase-two work around QBO unattended reliability and typed program metrics before expanding interpretation scope.

  4. Keep runbook and dashboard docs synchronized using the documentation precedence map (docs/documentation/source-of-truth.md) so handoff instructions stay aligned with live behavior.
